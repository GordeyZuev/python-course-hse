# Как получать обновления курса и сдавать решения

Рабочая схема: получить обновления → решить задачи → проверить локально →
отправить готовую попытку. У каждого студента один приватный репозиторий на весь
курс. Создавать отдельный репозиторий для каждого ДЗ не нужно.

## Два источника в Git

| Имя | Что это | Для чего используется |
|---|---|---|
| `origin` | Ваш приватный репозиторий в `ai-hse-python` | Сдача решений; получение настроек проверки и новых заготовок |
| `upstream` | Общие материалы `GordeyZuev/python-course-hse` | Условия, публичные тесты, лекции и исправления |

Ваша рабочая ветка — `main`. Ветка общих материалов — **`course_2026`**.
Названия веток здесь разные; `upstream/main` для этого курса не подходит.

Это та же модель «личный репозиторий + upstream», что описана в
[инструкции курса ШАДа](https://github.com/K1oppert/ysda-public-2026-fall/blob/main/SETUP.md).
В нашем курсе перед upstream также обновляется origin: преподаватель добавляет
туда настройки сдачи. Отдельный скрипт обновления не требуется.

## Настроить один раз

Клонируйте выданный вам приватный репозиторий и примите приглашение GitHub,
если ещё не сделали этого. Работайте в его папке, а не в скачанном ZIP.

Проверьте источники:

```bash
git remote -v
```

`origin` должен указывать на ваш репозиторий в `ai-hse-python`.
Если `upstream` ещё не настроен:

```bash
git remote add upstream https://github.com/GordeyZuev/python-course-hse.git
```

Если он уже настроен правильно, добавлять его снова не нужно.

## Обновить перед началом работы

Сначала выполните `git status`. Если есть свои изменения, сохраните их локальным
коммитом. Добавляйте в коммит конкретные файлы решений, а не всё содержимое
папки вместе с окружением и временными файлами. Локальный коммит попытку не тратит.
Если решали в отдельной ветке, объедините её с `main`, когда готовы работать в ней.

Команды выполняйте последовательно, проверяя результат каждой:

```bash
git switch main
git fetch origin
git merge --no-edit origin/main
git fetch upstream
git merge --no-edit upstream/course_2026
```

Они обновляют только вашу локальную копию. **Сразу делать push не нужно.**
Повторяйте обновление перед новым ДЗ и после объявления об исправлении тестов.
Существующие решения сохраняются при обычном слиянии; если обе стороны изменили
один участок, Git остановится для разрешения конфликта.

## Что происходит при выдаче нового ДЗ

Преподаватель публикует условия, заготовки, тесты и `homework.json`.
Система сначала добавляет отсутствующие материалы в ваш origin, потом включает
проверку нового ДЗ. Эта служебная доставка попытку не тратит и не заменяет
существующие файлы решений.

Начинайте работу после объявления, что ДЗ выдано, и получите **оба** источника
командами выше. Так заготовки из upstream совпадут с уже доставленными в origin.
Если начали решать до завершения обновления, возможно слияние с конфликтом
`add/add`: файл уже создан и у вас, и в общих материалах. Это разрешается Git,
а не повторным клонированием поверх своей работы.

## Проверить и отправить попытку

Запустите локальные тесты и грейдер. Для HW 1, например:

```bash
python Other/tools/grade.py --hw pro-hw1
```

Код другого ДЗ берётся из `id` в его `homework.json`.
После сохранения решений коммитом проверьте, что собираетесь отправить:

```bash
git fetch origin
git merge --no-edit origin/main
git diff --name-only origin/main HEAD
git push origin main
```

После `merge` с конфликтом остановитесь и разрешите его до следующих команд.
Список перед push показывает разницу с последним полученным состоянием origin.
Если в нём есть файлы решений двух ДЗ, будут потрачены две попытки — по одной
на каждое ДЗ. Все задачи соответствующего ДЗ проверяются целиком.

| Действие | Расходует попытку? |
|---|---|
| Локальный тест, `git add`, `git commit`, `fetch`, `merge` | Нет |
| Push изменений только условий, README или тестов | Нет |
| Push в `main`, изменяющий отслеживаемые файлы решений | Да |
| Повторный запуск того же Actions run после технического сбоя | Новую попытку не создаёт |

Проверка смотрит на всю разницу, отправленную одним push, а не только на последний
коммит. Поэтому push «только с обновлениями» тоже будет сдачей, если в нём есть
ранее не отправленные решения. Переименование или удаление файла решения также
может запустить проверку: сохраняйте исходные пути и имена.

Получение обновлений само по себе не расходует попытку. Но если новый файл
решения ещё отсутствовал в origin, его первая отправка туда считается изменением
решения. Именно поэтому сначала нужно получать origin и ждать завершения выдачи.

## Если Git остановился

**Есть незакоммиченные изменения.** Сохраните свою работу локальным коммитом и
повторите обновление. Git обычно отказывается перезаписывать такие изменения.

**Merge conflict / add/add.** Выполните `git status`, откройте конфликтующие файлы,
сохраните нужный код и уберите маркеры конфликта. Затем `git add` для исправленных
файлов и `git merge --continue`. Не выбирайте механически «принять всё из upstream»:
это может заменить решение заготовкой. Если нужно отменить текущую попытку
слияния, выполните `git merge --abort`; ваши ранее сохранённые коммиты останутся.

**Push rejected / non-fast-forward.** Origin успел обновиться. Снова выполните
`git fetch origin`, затем `git merge --no-edit origin/main`, проверьте результат
и повторите обычный push. `push --force` для обновления курса не нужен.

**Нет upstream / указан неверный адрес.** Сверьте `git remote -v`. Для изменения
уже существующего адреса используется `git remote set-url upstream` с адресом
общего репозитория, указанным выше.

**README показывает новую версию, а Actions — другую.** Локальные материалы и
официальный грейдер обновляются отдельными действиями. В Actions используется
утверждённая преподавателем версия. Изменение своих тестов, `homework.json` или
workflow не меняет официальные правила. Сообщите преподавателю о расхождении.

## Где смотреть результат

Сразу после push: **Actions → Submit код-ДЗ → Summary** в вашем репозитории.
Ведомость и Issue «Оценки и проверки» обновляются при служебном сборе, обычно
раз в три часа. На ДЗ четыре попытки, в зачёт идёт лучший общий результат одной
своевременной попытки. Поздняя попытка в пределах лимита тоже показывает тесты,
но её зачётный балл равен нулю. Ручная оценка ассистента имеет приоритет.
